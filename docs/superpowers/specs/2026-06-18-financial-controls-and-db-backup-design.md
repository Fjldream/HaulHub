# 财务修正、月度锁账与轻量数据库备份设计

## 背景

HaulHub 已经支持趟次结算、补录已完成账单、车辆维修费、司机工资和利润统计。上线后最容易出问题的不是录入本身，而是历史数据被误改、误删，或者补录日期、工资月份、维修月份录错后没有安全的修正方式。

本设计目标是增强财务数据可靠性，同时不改变已有核心功能和 UI 使用习惯。

## 目标

- 管理员可以对影响利润的数据做作废或调整，而不是直接删除。
- 月度利润确认后可以结账锁定，防止历史月份被误改。
- 需要修改已结账月份时，必须先反结账并填写原因。
- 利润统计能够正确排除作废数据，并展示调整后的真实利润。
- 只做轻量数据库备份，不备份图片、附件、代码和构建产物。
- 备份策略必须适配小容量服务器，不能因为自动备份把磁盘写满。
- 不影响现有司机端、管理员端、Web 后台已有功能和 UI 正常使用。

## 非目标

- 第一期不做图片、附件、上传目录备份。
- 第一期不做完整服务器镜像或代码目录备份。
- 第一期不做复杂审批流，只做管理员操作确认、原因记录和审计日志。
- 第一期不重做利润页 UI，只在必要位置增加锁账、作废、调整相关提示。
- 第一期 App 端不开放复杂财务作废、反结账、备份管理能力。

## 范围

第一期覆盖这些会直接影响利润的数据：

- 补录已完成账单。
- 正常趟次结算生成的结算快照。
- 司机工资。
- 车辆维修费用。
- 其他费用或趟次费用。

## 方案选择

### 方案 A：只做数据库月备份

优点是改动小、服务器资源占用低。缺点是不能解决业务误操作，真遇到账录错，只能恢复整个数据库，恢复成本高，还可能覆盖后续正常数据。

### 方案 B：只做财务作废、调整和月度锁账

优点是直接解决账务修正和历史月份保护。缺点是缺少灾备兜底，数据库损坏或部署误操作时恢复能力弱。

### 方案 C：财务作废、调整、月度锁账，加轻量数据库月备份

这是推荐方案。业务层面用作废、调整和锁账保护利润口径；运维层面只备份数据库并自动清理旧备份，兼顾可靠性和服务器容量。

## 财务修正模型

影响利润的数据不再使用物理删除作为主流程。管理员需要修正时，系统提供两类动作：

- 作废：原记录不再计入利润统计，但保留原始数据和审计日志。
- 调整：新增一条调整记录或修改记录状态，保留调整前后金额、原因和操作人。

建议新增统一字段到利润相关模型，或通过独立修正表表达：

- `voidedAt`：作废时间。
- `voidedById`：作废操作人。
- `voidReason`：作废原因。
- `adjustedFromId`：如果是调整记录，指向原记录。
- `adjustReason`：调整原因。
- `createdById`、`updatedById`：记录录入和最后修改责任人。

利润统计只读取有效记录：

- 未作废的 `SettlementSnapshot`。
- 未作废的 `DriverPayroll`。
- 未作废的维修费。
- 未作废的费用记录。

如果某条历史记录被调整，报表展示调整后的有效金额，审计页保留原记录和调整链路。

## 月度结账锁定

新增月度结账状态，按团队和月份管理。

建议新增 `FinancialPeriodClose`：

- `teamId`：团队。
- `periodMonth`：月份，格式 `YYYY-MM`。
- `status`：`open`、`closed`。
- `closedAt`、`closedById`：结账信息。
- `closeNote`：结账备注。
- `reopenedAt`、`reopenedById`：反结账信息。
- `reopenReason`：反结账原因。

锁账规则：

- 未结账月份允许正常新增、修改、作废。
- 已结账月份禁止新增、修改、作废会影响利润的数据。
- 已结账月份需要修改时，管理员必须先反结账并填写原因。
- 反结账后，该月份回到可操作状态。
- 再次结账时重新记录结账人、结账时间和备注。

系统判断财务归属月份时使用业务月份：

- 趟次和补录账单按 `settledAt` 所在月份。
- 司机工资按工资月份。
- 维修费用按维修日期所在月份。
- 趟次费用按趟次结算归属月份。

## Web 后台 UI

新增入口尽量放在现有财务、利润或系统设置相关子菜单中，不改变已有页面主结构。

建议页面：

- 利润统计：增加结账状态提示。已结账月份显示“已结账”，未结账月份显示“未结账”。
- 月度利润：增加“结账 / 反结账”操作入口。
- 财务调整记录：查看作废、调整、反结账操作历史。
- 备份记录：查看最近数据库备份时间、文件大小、状态和失败原因。

关键交互：

- 作废或反结账必须弹窗确认。
- 弹窗必须填写原因。
- 危险操作使用当前系统危险色和按钮风格，不新增突兀样式。
- 作废成功后列表保留记录状态，避免用户误以为数据丢失。
- 已结账导致不能操作时，用小弹窗或页面提示说明原因和处理方式。

## App 端影响

第一期 App 端不新增复杂财务控制入口。

需要适配的地方：

- 管理员 App 利润统计继续展示正确利润结果。
- 已作废数据不出现在有效利润中。
- 如果 App 端已有维修、补录、工资相关入口，提交时需要遵守月度锁账限制。
- 司机端不展示利润、工资、备份、结账和财务调整信息。

## 数据库月备份

备份只覆盖数据库文件或数据库导出数据，不覆盖：

- 上传图片。
- 票据附件。
- 代码目录。
- `node_modules`。
- 构建产物。
- 日志文件。

默认策略：

- 每月 1 日凌晨 3 点自动备份一次数据库。
- 保留最近 12 个月备份。
- 超过 12 个月的备份自动删除。
- 文件名包含日期和环境，例如 `haulhub-db-2026-07-01.sqlite.gz`。
- 备份目录单独放置，例如 `/home/ubuntu/haulhub-backups/monthly-db`。

容量保护：

- 备份前检查磁盘剩余空间。
- 如果剩余空间低于 2GB，跳过本次备份并记录失败原因。
- 备份目录总大小建议限制为 2GB。
- 如果备份目录超过限制，优先删除最旧备份，再尝试创建新备份。
- 如果删除旧备份后仍然空间不足，跳过本次备份并记录日志。
- 备份任务失败不能影响 API、Web 或 App 正常运行。

备份记录：

- 记录备份开始时间、结束时间、状态、文件大小、文件路径和失败原因。
- 后台只展示摘要信息，不提供随意下载数据库能力，避免数据泄露。
- 恢复数据库不做在线按钮，仍由运维手动执行，避免误恢复覆盖线上数据。

## 权限和审计

只有管理员可以：

- 作废财务记录。
- 录入调整记录。
- 结账。
- 反结账。
- 查看备份记录。

每次关键操作都写入 `AuditLog`：

- 操作人。
- 团队。
- 操作类型。
- 目标对象。
- 操作前数据。
- 操作后数据。
- 原因。
- 操作时间。

## API 设计

建议新增或扩展以下接口：

- `GET /admin/financial-periods`：查询月份结账状态。
- `POST /admin/financial-periods/:month/close`：月度结账。
- `POST /admin/financial-periods/:month/reopen`：反结账。
- `POST /admin/financial-adjustments`：创建作废或调整记录。
- `GET /admin/financial-adjustments`：查询调整和作废历史。
- `GET /admin/backups/database`：查询数据库备份记录。

所有写入接口在落库前都要校验：

- 当前团队是否匹配。
- 当前用户是否管理员。
- 数据归属月份是否已结账。
- 金额、日期、枚举值是否合法。
- 作废或反结账原因是否填写。

## 利润统计规则

利润统计继续以现有口径为基础，但增加有效性过滤：

```text
净利润 = 有效运费收入 - 有效趟次费用 - 有效维修费用 - 有效司机工资 - 有效其他调整支出 + 有效调整收入
```

需要保持：

- 周利润不强行计入按月归属的司机工资。
- 月利润计入该月工资、维修、趟次结算和有效调整。
- 年利润汇总 12 个月有效数据。
- 司机维度仍展示趟次数量，不统计司机利润。
- 协同司机趟次按现有规则计入趟次数量。

## 错误处理

- 已结账月份禁止修改时，前端用当前系统风格的小弹窗提示。
- 后端返回明确错误码和中文错误信息。
- 数据库备份失败只记录状态和日志，不阻塞主业务。
- 金额、日期、枚举类型错误必须在前端尽量拦截，后端再次校验。

## 测试计划

后端测试：

- 未结账月份可以新增、作废、调整财务记录。
- 已结账月份禁止新增、作废、调整财务记录。
- 反结账后可以再次操作。
- 作废后的账单不再计入利润。
- 调整后的金额进入月利润和年利润。
- 司机工资仍按工资月份计入月利润和年利润。
- 周利润不计入司机工资。
- 协同司机趟次数量统计不受利润修正影响。
- 备份目录超过 2GB 时清理旧备份。
- 磁盘剩余空间不足 2GB 时跳过备份并记录失败。

前端测试：

- 利润页显示结账状态。
- 已结账月份操作入口不可用或给出明确提示。
- 作废和反结账弹窗必须填写原因。
- 财务调整记录列表能展示操作人、时间、对象、原因和金额影响。
- 备份记录页能展示最近备份状态。
- 现有登录页、趟次、维修、费用、利润、资产等页面样式不被无关改动影响。

回归测试：

- Web 后台补录账单正常保存。
- Web 后台非法输入不会导致页面崩溃。
- App 管理员端补录和维修入口正常。
- 司机端我的小票、费用上传、通知不受影响。
- 利润统计在无作废数据时与当前结果保持一致。

## 上线策略

1. 先上线数据库结构和后端校验，默认所有月份为未结账。
2. 再上线 Web 后台结账、反结账和作废入口。
3. 最后开启每月数据库备份定时任务。
4. 上线后先人工触发一次数据库备份测试，确认文件大小、清理规则和失败日志正常。

## 风险控制

- 默认不自动锁定历史月份，避免上线后突然影响现有录入。
- 结账动作由管理员主动执行。
- 作废不删除原数据，降低误操作损失。
- 恢复数据库不做网页按钮，避免误点造成线上数据回退。
- 备份有数量和容量双重限制，降低服务器被写满风险。
